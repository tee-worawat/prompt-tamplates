How eval fits into orchestration

  1. Worker startup: register_tracer once (same as L5 notebook)
  2. Inside each activity: OpenInference + @tracer.tool — stamp activity.info().workflow_id

  4. Gate (optional): critique_draft blocks bad drafts in Temporal; Phoenix scores the same spans later

Lessons 0–2 · Decompose agents

Ask: which unit of work failed?

Concept: agent ≠ model

Thumbs-up on the final answer hides failures in the middle. Split the agent into three eval targets — each with its own score and its own fix.

① Router eval

Question: did we pick the right tool for the job?

Our lab

User: "Create a bar chart of sales by store" → agent calls analyze_sales_data instead of generate_visualization. Prose about charts, no chart code.

Real world

Bank support bot: "Dispute this charge" → agent searches FAQ instead of opening a create_dispute_case ticket. Answer sounds helpful; wrong workflow.

Dev copilot: "Fix the failing test" → agent edits docs instead of calling run_tests.

② Skill eval

Question: once the tool was chosen, did that step actually work?

Our lab

Router correctly calls lookup_sales_data, but SQL filters store 99 when the user asked for store 1320. Or chart code throws on exec.

Real world

HR assistant: right tool (query_payroll_db), but SQL uses last month instead of the pay period in the question.

Ops agent: calls restart_service on prod when user meant staging — right tool family, wrong args.

③ Trajectory eval

Question: did we take a short path, or wander?

Our lab

Same intent: "mean basket size" vs "avg qty per transaction" — one phrasing takes 6 messages, another 12. Both may look "correct."

Real world

Travel agent: books a flight in 3 tool calls for one user, 9 calls for another asking the same thing differently — extra cost + latency.

SRE runbook bot: loops lookup → analyze → lookup again before escalating — should have paged on call 2.

Debug discipline — match symptom to eval

Wrong tool → router · Wrong SQL / broken code / bad prose → skill · Too many hops, same answer → trajectory. Chart wrong? Don't rewrite SYSTEM_PROMPT first — find which eval would fail.

Lesson 3 · L3/L3.ipynb · Build the agent

The router is a while-loop around tools

Concept: function calling = agent router

Each turn the LLM returns either tool_calls (keep looping) or final content (stop). handle_tool_calls dispatches name + JSON args to Python. Multi-hop questions need multiple iterations in one run_agent call.

Practical examples
Try in L3.ipynb

Multi-hop: "Graph of sales by store in Nov 2021 + what trends you see" → expect lookup → generate_visualization → analyze → final text. Count while-loop iterations.

Break it: add tool name to tools[] only → KeyError in handle_tool_calls.

Real world

Sales copilot: user asks for chart + summary → agent must chain query_db → render_chart → summarize — same loop pattern as our three tools.

IT helpdesk: "Reset password and email confirmation" → two tool calls in one session, not one bloated LLM guess.

while True:
    response = client.chat.completions.create(
        model=MODEL, messages=messages, tools=tools)
    if response.choices[0].message.tool_calls:
        messages = handle_tool_calls(tool_calls, messages)
    else:
        return response.choices[0].message.content

Lessons 6–7 · L7/L7.ipynb · Router & skill evals

Forensic eval: query traces → score → log back

Concept: feedback functions on spans

Run agent on a question battery → SpanQuery filters Phoenix spans → llm_classify (judge) or exec (code) → log_evaluations writes labels onto spans in the UI. Judge wrapped in suppress_tracing() so grader traffic ≠ agent traffic.

Practical examples
Try in L7.ipynb

"Create a bar chart showing total sales by store" → Tool Calling Eval: correct if generate_visualization chosen. Runnable Code Eval: exec the returned matplotlib string.

"What was total revenue?" → Tool Calling ✓ but SQL Gen ✗ if query sums wrong column — two scores, one run.

Real world

Insurance claims bot: nightly job runs same llm_classify on 5% of live traces — did agent call fetch_policy before approve_claim?

Code assistant: judge labels tool choice; CI separately runs pytest on generated patch — dual signal like our judge + exec.

Lessons 8–9 · L9/L9.ipynb · Trajectory / convergence

Trajectory = path economics, not correctness

Concept: convergence score

Same intent, many wordings. A brittle router takes extra hops on paraphrases. Convergence = shortest path in the batch ÷ this run's path length. 1.0 = as efficient as the best sibling; 0.5 = twice as many messages. Always pair with quality evals — short wrong beats long right.

Practical examples
Try in L9.ipynb

Upload 17-question dataset → run experiment → evaluate_path_length. Row scores 0.5? That paraphrase used twice the messages of the best sibling in the batch.

Open Phoenix experiment compare view — read format_message_steps for the slow row vs the fast one.

Real world

Procurement agent: "Cheapest vendor for 500 laptops" vs "Lowest price supplier, 500 units" — same intent; 8 vs 4 API calls = billing surprise.

Clinical triage bot: convergence drop after prompt change flags regression even when answers still "look fine" to clinicians.

def run_agent_and_track_path(example):

Lessons 10–11 · L11/L11.ipynb · Structured experiments

Experiments = regression suite for prompt changes

Concept: span eval vs experiment

L7 is forensic — score traces that already happened. L11 is scientific — same dataset + evaluators, change one variable (e.g. SQL prompt), compare Overall Experiment v1 vs v2. Each row has input, task output, and expected golden fields.

Practical examples
Try in L11.ipynb

Run Overall Experiment v1 → pick failing row → note which evaluator failed (e.g. evaluate_sql_result).

update_sql_gen_prompt("... Think before you respond.") → v2 → compare SQL scores in Phoenix, not gut feel.

Real world

Product team: 40 golden support questions in Phoenix dataset — PR that changes router prompt must pass experiment v2 ≥ v1 on tool-calling + sql_result.

Fintech: entity_correctness catches "account ending 4521" in answer when user asked about 4529 — clarity alone would pass.

Lesson 12 · Improving LLM-as-a-judge

The judge is a model — it also needs eval

Concept: rails + explanation + dual signal

Rails force parseable labels (correct/incorrect), not free prose scores. Explanation before LABEL reduces reverse-justification. If the judge is noisy, every experiment is a random number generator — spot-check 20 labels yourself (golden slice).

Practical examples
In this repo

No GOOGLE_API_KEY → MockEvalModel often labels everything correct. That's expected — teaches eval structure. With live Gemini, spot-check 10 labels in Phoenix explanations.

Real world

Content moderation: judge says "safe" on subtle policy violation — human golden slice catches it. Recruiting bot: judge marks answer "clear" but omits salary range asked in question.

Lesson 13 · Monitoring agents

Offline eval → sampled production loop

Concept: same evals, different schedule

L7 queried a batch you just generated. Monitoring runs the same SpanQuery + llm_classify on a sample of live AgentRun spans. Spike in tool-calling errors → alert → new experiment on failing questions. Stable span names (router_call, lookup_sales_data) are the contract between app and eval jobs.

Practical examples
From labs → prod

Same SpanQuery + llm_classify from L7, scheduled nightly on project evaluating-agent. Alert if Tool Calling incorrect rate > 10% over 24h.

Real world

Retail chatbot: Black Friday spike in unrunnable chart % → on-call checks viz prompt deploy from yesterday. Internal wiki agent: path length drift after embedding model swap → router confused, not retrieval.

Week 5 + Week 7 · Phoenix on Temporal

Temporal: survive · Phoenix: chose well

Concept: two systems, one pipeline

Temporal retries infrastructure failure (timeout, worker down). Phoenix scores intelligence failure (wrong tool, bad SQL). Instrument activities, not the workflow. Join on workflow_id. Week 5 critique_draft is judge-as-gate; Phoenix experiments are judge-offline.

Practical examples
Plug-in sketch

Week 5 draft_answer activity → wrap with OpenInference + stamp activity.info().workflow_id. Offline: SpanQuery filter activity_type == "draft_answer" → same Tool Calling eval as L7.
